Each mode is described by a `config.jsonc` file at the root of the mode directory. One
`config.jsonc` (and the `.lwmode` file `lw mode build` produces from it) always describes exactly
one mode. Config files are parsed following the [json5](https://json5.org/) specification (so
comments and trailing commas are allowed).

## Example

```jsonc
{
  "$schema": "https://lewdware.github.com/config.schema.json",
  "id": "5e8f9e0a-6b1c-4d2e-8f3a-9b0c1d2e3f4a",
  "name": "My Mode",
  "version": "1.0.0",
  "author": "your-name",
  "entrypoint": "src/main.lua",
  "options": {
    "popup_frequency": {
      "label": "Popup frequency (seconds)",
      "description": "How often popups appear",
      "type": "number",
      "default": 1,
      "min": 0.1,
      "max": 10,
      "step": 0.1
    }
  }
}
```

## Top-level fields

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | `string` (UUID) | Yes | Stable identity for this mode, used to scope `lewdware.storage` across restarts and rebuilds. Generated once by `lw mode new` — don't edit this by hand. |
| `name` | `string` | Yes | The display name shown to the user in the config app. |
| `version` | `string` | No | Version string, e.g. `"1.0.0"`. |
| `author` | `string` | No | Author name. |
| `include` | `string[]` | No | Paths of directories or files of Lua code to bundle (e.g. `["src"]`). |
| `entrypoint` | `string` | Yes | Path to the main Lua file, relative to the config file. |
| `needs_permissions` | `string[]` | No | [Permissions](#permissions) the mode uses no matter how it is configured. |
| `options` | `object` | No | Map of option keys to [option definitions](#options). |

## Options

Options expose configurable values to the user. At runtime, each option's current value is
accessible in Lua as `lewdware.config["key"]`, where `"key"` is the option's key in the `options`
map.

All option types share these base fields:

| Field | Type | Required | Description |
|---|---|---|---|
| `label` | `string` | Yes | Label shown to the user in the config app. |
| `description` | `string` | No | Optional explanation shown below the label. |
| `type` | `string` | Yes | One of `"integer"`, `"number"`, `"string"`, `"boolean"`, `"enum"`. |
| `needs_permissions` | `string[]` | No | [Permissions](#permissions) this option uses. |

The remaining fields depend on `type`:

## Permissions

Three things a mode can do reach outside its own windows, and each is behind a permission the user
owns and can switch off at any time: `set_wallpaper` (set the desktop wallpaper), `open_links` (open a
link in the browser) and `send_notifications` (show a desktop notification). `open_links` starts switched
**off**.

A mode can't ask for these, and declaring `needs_permissions` grants nothing — when a permission is denied
the corresponding call simply does nothing, and Lua gets `false` back, exactly as if the action
had failed for any other reason. What `needs_permissions` does is let the config app explain *why* nothing
will happen, next to the option responsible, and offer to turn the permission on right there.

```jsonc
"web_opening_enabled": {
  "label": "Open web links",
  "type": "boolean",
  "default": true,
  "needs_permissions": ["open_links"]
}
```

Put `needs_permissions` on the narrowest thing that needs it:

- **On an option** — the usual case. Best of all on the boolean that switches the feature on,
  since a requirement is only reported while the option is actually in use: a boolean set to
  `false`, a disabled `optional`, or anything hidden by `show_when` raises no notice.
- **On a group** — when everything inside it depends on the same permission.
- **At the top level** — only when the mode uses a permission no matter how it is configured, so
  there is no option to attach it to.
